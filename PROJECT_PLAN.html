01 Executive summary

A bounded, parallelizable workstream — not a big-bang cutover.

Project Atlas Phase 2 retires direct SQL Server access from every consuming application (Boomi flows, EDI engines, RUDI/COMPASS, Salesforce sync, Esker AR connector, internal services) and replaces it with a coherent set of 19 REST APIs built on the USV Stack template. The legacy database surface (~250 canonical procs across 4 SQL Server databases) consolidates to ~165 endpoints, with vendor-specific clones, dated revisions, and version variants collapsed behind parameter-driven contracts.

The work breaks into seven sequential phases over ~17 months with substantial parallelism within each phase. Two teams own the work end-to-end: a Platform team owns the foundation (AlloyDB, USV Stack template, shared infra, view ports, CI/CD) and an Integration team owns all 19 APIs and consumer cutovers. Within the Integration team, work is organized into rotating pods aligned to each phase's API cluster, but ownership and on-call responsibility stays with one team.

Key architectural decision: API repositories query the d365.* source schema directly in AlloyDB. The ~290 dbo.* base-table mirror views in integration-idb are NOT being ported — they were a query-convenience mirror in the legacy stack and are unnecessary once the API queries d365 directly. This drops the view-porting workload from ~360 to ~60 (just the USV business views).

03 Teams

Two teams own the work end-to-end. Platform owns the foundation; Integration owns every API and every consumer cutover.

Platform Team

4–6 eng

Foundation · data layer, template, shared infrastructure

OwnsEverything underneath the API layer: AlloyDB infrastructure, the d365.* source schema readiness, ports of the ~60 in-scope USV business views, the USV Stack template, CI/CD, shared libraries, observability, and the parity-testing harness.

Specifically
· AlloyDB d365.* schema sign-off (Phase 0 gate)
· Port the ~60 USV business views (usvprogramcustomer, usvecoresprodtiresattributes, etc.)
· Boomi xref-table DDL + Boomi DB-role provisioning
· Materialized-view strategy for SalesforceCustomerV2 with refresh
· USV Stack template hardening; shared NuGet packages (Usv.Stack.Auth, Common.Data.*)
· CI/CD pipeline templates, dev/test AlloyDB instances, secrets management
· Shared OIDC auth helper, date-conversion mapper, connection-pool config
· Observability (logs / metrics / traces / dashboards / alerting)
· Parity-testing harness (run legacy proc + new API, diff outputs)
· Schema-migration tooling and playbook
· Phase 6: revoke legacy DB access, decommission source SQL Server instances

CadenceFront-loaded in Phase 0 (~2 months of heads-down foundation work), then steady-state support throughout Phases 1–5 (template updates, schema additions, infra issues), then leads Phase 6 decommission.

Key external dependenciesSource-system DBAs (for d365 readiness, vN production-version confirmation), Salesforce admin (owner-ID environment confirmation), networking/security (DB-role provisioning).

Integration Team

10–14 eng + PO

Delivery · all 19 APIs + all consumer cutovers

OwnsEvery API project, every endpoint, every consumer migration. Builds the APIs in dependency order across Phases 1–5; runs cutover sprints continuously from Phase 1 onward.

All 19 APIs
Pilot (P1): Routes, Platform, RudiCompass, SalesforceIntegration
Masters (P2): Customer, Vendor, Warehouse, Product
Dependents (P3): Program, Delivery, PurchaseOrder, Invoice, TransferOrder
Composite (P4): OrderStatus, Finance
Complex (P5): VendorProgram, InvoiceMatching, EdiOutbound, EdiInbound

Internal organizationTeam rotates into pods of 2–4 engineers per phase, aligned to that phase's API cluster. The pods aren't separate teams — they're how the team allocates its bandwidth across concurrent APIs within a phase. Pod composition reshuffles each phase so domain knowledge spreads across the team and on-call burden distributes.

Cutover responsibilities
· Boomi flow reconfig (Salesforce sync, PO flows, others)
· EDI engine cutover (810/850/855/856 inbound & outbound)
· RUDI/COMPASS cutover
· Esker AR connector cutover (external vendor coordination)
· Internal services migration off direct DB access
· Per-API parity sign-off before legacy access is revoked (handed to Platform team for revocation)

CadenceEach shipped API triggers a cutover sprint for its consumers. Legacy DB access for that API's source procs/views is flagged for revocation only after 30 days of clean parity reports.

Why two teams, not nine: the original 9-team breakdown optimized for parallel velocity but added coordination overhead and ownership ambiguity at API boundaries. Consolidating to two teams keeps parallelism inside the Integration team (via phase-aligned pods) while making accountability obvious: Platform owns “does it run?”, Integration owns “does it work and is it being used?”. The trade-off is that the Integration team needs strong internal pod coordination — one tech lead who keeps the dependency graph in their head across phases.

05 Phase detail

Each phase has a fixed gate: the next phase doesn't start until the gate condition is met.

PHASE 0

Foundation — sign-offs and template hardening

~2 months
Lead team
Platform (Integration involved in template-feedback loop)
APIs shipped
None — foundation work
Gate to next phase
d365 schema sign-off + green smoke build on hardened template

Goals

  • Confirm d365.* source tables present in AlloyDB at expected shape (CDC/DMS pipeline coverage check)
  • Port the ~60 in-scope USV business views to AlloyDB
  • Harden the USV Stack template (shared auth, date mapper, connection-pool, observability)
  • Stand up CI/CD pipeline templates and dev/test AlloyDB instances
  • Stand up parity-testing harness (run legacy proc + new API, diff outputs)

Decisions to lock in this phase

  • AlloyDB schema naming (keep ais/eta/boomi/rudi/d365 verbatim, or rename per USV Stack examples)

  • vN collapsing: confirm with source team which version is in production for each spOrderStatusDetailv3-v15, spBackorderSummaryV2/V3, spGetInvoiceRemainderv2-v4, spRWAInvoiceMatchingServicev2-v9

Success criteria

  • One reference API project builds clean against the hardened template, hits real AlloyDB, returns one row from d365.custtable
  • Parity harness runs: same input to legacy proc + reference API produces matched output
  • All open questions in master plan §I have written answers

Why these four first

  • RudiCompass — 4 endpoints, smallest new API. Validates building a brand-new bounded context (no existing legacy proc patterns to follow).
  • SalesforceIntegration — 6 view-based read-only endpoints with CST timezone handling and a heavy materialized-view candidate. Validates view sources and the boomi xref-table pattern.

Cutover targets

  • Boomi flows: cut Salesforce sync flows from direct DB to /salesforce/*
  • RUDI/COMPASS: cut from rudi.COMPASSValidate* direct calls to /compass/*
  • ETA-internal consumers cut to /eta/*

Success criteria

  • 4 APIs deployed to prod, on-call rotation established
  • SLO baseline measured (latency p95, error rate, throughput)
  • Materialized-view refresh strategy proven on SalesforceCustomerV2
  • Template feedback loop closed: any pain points found by Foundation Squad fixed in template before squads scale up

Goals

  • Revoke read-only DB roles from all consumer applications
  • Drop the ~125 dead-code variant procs flagged in §A triage (backups, dated revisions, version-suffixed)

07 Risks

Top risks and mitigations. Severity reflects likelihood × impact, not just impact alone.

d365 schema not actually ready in AlloyDB High

Phase 0 assumes the data-platform team has the d365.* tables landed in AlloyDB at the right shape. If CDC/DMS coverage is incomplete, every API project blocks immediately.

Mitigation: dedicated Phase 0 sign-off gate; written confirmation per table; smoke-test query against each Phase 1 API's source tables before that team starts work.
vN proc version drift hides production behavior High

Procs like spOrderStatusDetailv3-v15 may not be byte-identical; consolidating to "the latest" may silently change behavior for some consumers.

Mitigation: Phase 0 source-team confirmation per vN family; parity-testing harness diffs API output against the production proc for 30 days before legacy access is revoked.
Esker / EDI cutover misses scheduled window High

External vendor schedules (Esker AR connector, EDI trading-partner test transactions) cannot slip without external impact. Phase 4 and Phase 5 both have hard external dependencies.

Mitigation: Migration team locks vendor cutover dates 3 months in advance; carry both code paths (DB + API) for 30 days post-cutover with feature-flagged rollback.
Hard-duplicate procs have drifted bodies Medium

5 known hard duplicates between ais and integration (USVOrderStatusDetail/Summary/SummaryByInvoiceAccount, USVCustomerLookup, USVCustomerLookupByCustRefAndGroup). If bodies have diverged, "consolidating" picks one consumer's behavior over another.

Mitigation: byte-compare in Phase 2 before consolidating; if drift exists, ship the union of both behaviors with an opt-in flag and document the difference.
RWA matching engine parity is hard to validate Medium

InvoiceMatching has the densest business logic in the codebase — return-reason resolution, IBS path branching, fractional quantity handling, discontinue/acquisition overrides. Hard to construct exhaustive parity test cases.

Mitigation: Phase 5 includes 30-day shadow-mode running (route real traffic to both; compare; alert on mismatch); ramp cutover from 10% to 100% over 4 weeks.
VendorProgram domain too large to ship as one Medium

16 endpoints, ~36 source objects, mixing SSP/TPNA/CMP/Sellout/DirectSales sub-domains. Single-API approach risks a long stabilization tail.

Mitigation: Phase 5 contingency to split into VendorProgram.Ssp / VendorProgram.Tpna / VendorProgram.Cmp if velocity stalls; decision gate at end of week 6 of phase.
Quarantined Esker procs cannot be made functional Medium

Esker_company_AF and Esker_OutsidePmts_AF are flagged QUARANTINED in source — they reference an excluded view (v_dirpartytable). If the dependency can't be resolved, those endpoints ship in a degraded state or not at all.

Mitigation: Phase 0 includes resolving the v_dirpartytable question; if unresolvable, design degraded-mode contracts (return what we can; flag missing fields) by Phase 4 start.
Consumer migration backlog grows unbounded Medium

If consumers don't migrate at the cadence APIs ship, Phase 6 decommission slips and the project doesn't actually finish (legacy access stays open).

Mitigation: Migration team cadence is one cutover sprint per shipped API; quarterly steering review of unmigrated consumer count; clear deprecation timeline communicated to all consumer owners at project kickoff.
Materialized view refresh on SalesforceCustomerV2 Low

~50 columns, 14 joins, GROUP BY of 50 columns — the heaviest endpoint. Refresh strategy (scheduled vs. CDC-triggered vs. logical replication) is undecided.

Mitigation: prototype in Phase 1 as part of SalesforceIntegration delivery; pick the simplest approach that meets Salesforce's delta-pull SLO.
Hardcoded constants miswire across environments Low

Vendor '100687' in spGetWDNonSig, Salesforce owner ID '0056e00000BuxsJ', responsibility-ID priority chain — if these promote to config without per-env values, non-prod miswires silently.

Mitigation: Phase 0 inventory of every hardcoded value; per-env config files reviewed by domain SMEs before each phase ships.
